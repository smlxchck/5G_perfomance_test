# Описание интерфейса

Калькулятор работает как веб-интерфейс на Streamlit. Интерфейс состоит из боковой панели параметров слева и основной области с результатами справа. После запуска симуляции результаты сохраняются в `session_state` - их можно листать, переключать вкладки и менять параметры отображения без повторного запуска.

---

## Боковая панель - параметры конфигурации

Здесь задаётся конфигурация соты и параметры симуляции. Все параметры применяются только после нажатия кнопки «Запустить симуляцию».

### Параметры конфигурации

**Режим дуплекса** - FDD или TDD.
- `FDD` (Frequency Division Duplex) - DL и UL активны одновременно на разных частотах. Каждому направлению своя полоса.
- `TDD` (Time Division Duplex) - DL и UL чередуются по времени в одной полосе по паттерну (например, DDDSU).

**SCS (нумерология), кГц** - расстояние между поднесущими OFDM. Варианты: 15, 30, 60 кГц.
- 15 кГц → μ=0, TTI = 1 мс (как в LTE)
- 30 кГц → μ=1, TTI = 0.5 мс
- 60 кГц → μ=2, TTI = 0.25 мс

Чем выше SCS, тем короче интервал планирования и больше вычислительная нагрузка на чип.

**Полоса (BW), МГц** - ширина частотного канала. Список доступных значений строится динамически из таблицы `prb_table` в зависимости от выбранной SCS - выбрать комбинацию, которой нет в стандарте 3GPP, физически невозможно. Например, для SCS=30 кГц доступны: 10, 15, 20, 25, 30, 40, 50, 60, 80, 100 МГц.

**TDD slot-паттерн (D/U/S)** - появляется только при выборе TDD. Строка из символов D (Downlink), U (Uplink), S (Special). По умолчанию `DDDSU` - типовая конфигурация для band n78/n41. Паттерн зацикливается по модулю длины.

**MIMO слои** - 1 или 2.
- 1 = SISO (одна антенна)
- 2 = 2×2 MIMO (два независимых пространственных потока)

Каждый дополнительный MIMO-слой удваивает количество RE и нагрузку на шину AXI.

### Параметры симуляции

**Длительность симуляции, TTI** - ползунок от 500 до 20000 с шагом 500. По умолчанию 6000.
Под ползунком показывается пересчёт в секунды реального времени: `≈ TTI × (1 / (SCS/15)) / 1000` секунд. Например, 6000 TTI при SCS=30 - это 3 секунды.

### RE-level визуализация

**Сколько PRB показать в RE-level графике** - ползунок от 10 до 273 с шагом 10. По умолчанию 50.
При `n_size_grid=273` (максимальная конфигурация 100 МГц / SCS=30) показывать все PRB бессмысленно - картинка получается слишком вытянутой и неразборчивой. По умолчанию показываем первые 50 PRB, начиная с нулевого.

### Кнопка запуска

**Запустить симуляцию** - основная кнопка. Создаёт `CellConfig`, вызывает `run_simulation`, сохраняет результаты в `session_state`. Во время расчёта показывается спиннер. После завершения выбранный TTI сбрасывается на самый загруженный.

## Верхние карточки-метрики

После запуска симуляции над вкладками появляются четыре карточки с ключевыми метриками.

### Cell DL Throughput

Реальная средняя скорость соты в нисходящем канале, Мбит/с. Считается как сумма всех бит DL за всю симуляцию, делённая на общее время в секундах. В отличие от теоретической пропускной способности (которая считается по формуле Шеннона для идеального канала), здесь учитывается реальное распределение MCS - у кого-то плохой SNR, у кого-то пакеты не поместились в сетку.

### AXI средняя

Средняя нагрузка на шину AXI за один TTI, байт. Суммируются все операции чтения и записи через шину для всех блоков конвейера (Encoder LDPC, QAM mapper, Gridmapper, Encoder Polar, PDCCH Gridmapper) по всем абонентам в TTI, потом усредняются. Эта метрика - ориентир для выбора пропускной способности внутренней шины SoC.

### AXI пиковая

Максимальная нагрузка на шину AXI за один TTI по всей симуляции, байт. Показывает, какой пропускной способности шины хватит, чтобы справиться с самым загруженным интервалом. Если заложить шину по «средней» - в пике будут потери; по «пиковой» - гарантированно справится, но возможен перерасход площади чипа.

### Записей в БД

Количество строк в итоговом DataFrame. По одной записи на каждого абонента в каждом направлении в каждом TTI, где он активен. Например, при 6000 TTI и 6 абонентах в среднем - порядка 70 000 записей (с учётом TDD-слотов без DL/UL и абонентов, не поместившихся в сетку).

## Вкладка «Консоль / метрики»

Текстовый отчёт в том же формате, что и при запуске `python calculator.py` из консоли. Содержит:

1. **Заголовок с конфигурацией** - duplex, BW, SCS, μ, NSizeGrid, длительность TTI.
2. **Всего записей в симуляции** - общее число строк в DataFrame.
3. **Фрагмент базы данных** - первые 10 строк DataFrame с колонками TTI, Direction, UE_ID, SNR, MCS, Resources, PRBs, Payload_Bits, Codec, AXI_Load_Bytes, PDCCH_AXI_Bytes.
4. **Пропускная способность соты (Cell Capacity)** - средний и пиковый объём переданных данных за один TTI (КБ), реальная средняя скорость (Мбит/с).
5. **Статистика по абонентам** - таблица с колонками: сколько каждый UE скачал (DL, КБ), отправил (UL, КБ), скорость DL (Мбит/с), скорость UL (Мбит/с).
6. **Нагрузка на шину AXI (Hardware Performance)** - суммы PDSCH AXI и PDCCH AXI за всю симуляцию, средняя и пиковая нагрузка на TTI.
7. **Использование кодеков LDPC** - сколько раз использовался Base Graph 1 и Base Graph 2.
8. **Рекомендация архитектуры буфера** - текстовая рекомендация: где нужен локальный SRAM, а где достаточно общего Shared RAM через AXI.

## Вкладка «Графики»

Четыре графика, каждый - отдельный вызов функции из `calculator.py`. Все строятся по уже посчитанному DataFrame и `dl_scenario`, при переключении параметров отображения симуляция не перезапускается.

### 1. Resource Grid - распределение PRB между UE

Горизонтальная полоса высотой 1 ячейка, по горизонтали - индексы PRB от 0 до `n_size_grid-1` (например, 0–273 для 100 МГц / SCS=30). Каждый PRB окрашен в цвет абонента, которому он выделен (палитра tab20). Свободные PRB - серые.

Показан TTI с максимальной суммарной загрузкой PRB по всем UE. Выбор делается так:
```python
best_tti = max(metrics["dl_scenario"], key=lambda t: sum(
    int(ue.format_prb.split('x')[0]) for ue in t.users))
```

### 2. RE-level Grid - детализация до поднесущих и символов

Главный график для понимания того, как устроен один слот. Показывает каждый Resource Element (1 поднесущая × 1 OFDM-символ) с цветовой кодировкой по типу канала.

**Оси:**
- X - индекс OFDM-символа (0–13, всего 14 символов в слоте при Normal CP).
- Y - индекс поднесущей, сгруппированной по PRB. Подписи «PRB 0», «PRB 3», «PRB 6» и т.д. - каждый PRB = 12 поднесущих.

**Цветовая кодировка:**
- **Серый** - пустой RE (не занят ни одним каналом).
- **Чёрный** - PDCCH (управляющий канал, символы 0–1). CORESET в начале слота.
- **Золотистый** - DM-RS (опорный сигнал демодуляции, символ 3). Front-loaded DM-RS.
- **Цветной** - PDSCH (данные абонента). Каждый UE - свой цвет из палитры tab20.

**Разделители зон (как в классических resource grid визуализаторах):**
- Сплошная толстая линия после символа 1 - граница PDCCH / данные.
- Пунктирные линии до и после символа 3 - границы DM-RS.

**Подписи зон снизу:** «PDCCH (Control)», «DM-RS (Reference)», «PDSCH (User Data)».

**Управление:**
- Ползунок «Выберите TTI для отображения» - от 0 до `num_ttis-1`. По умолчанию выбран самый загруженный.
- Поле ввода «Или введите номер TTI вручную» + кнопка «Перейти» - для прямого перехода к нужному интервалу (ползунок и поле синхронизированы через `session_state`).
- Метрика «Активных UE» - сколько абонентов активно в выбранном TTI.

**Легенда справа:** список всех каналов с цветами и, для каждого UE, его ID, MCS и SNR.

**Что показывает:** как именно планировщик упаковал абонентов в слоте. Видно, что PDCCH всегда занимает символы 0–1 на всех поднесущих (CORESET), DM-RS идёт одним столбцом в символе 3, а PDSCH разбит между абонентами по диапазонам PRB. Сравнивая разные TTI, можно увидеть, как меняется состав абонентов и распределение ресурсов во времени.

### 3. Динамика активных абонентов

Линейный график количества уникальных UE в DL по времени. Ось X - номер TTI, ось Y - количество активных абонентов (0–15). Стиль `steps-post` подчёркивает дискретность - состав меняется только в моменты добавления/удаления абонентов.

В заголовке указана длительность симуляции в секундах: `num_ttis × tti_duration_ms / 1000`.

**Что показывает:** насколько динамична сота. При `change_probability=0.0001` на TTI состав меняется редко - на графике это длинные горизонтальные участки с редкими ступеньками. Если поставить вероятность выше - ступеньки станут чаще.

### 4. Распределение MCS (28 индексов)

Столбчатая гистограмма: по оси X - все 28 индексов MCS (0–27), по оси Y - сколько раз каждый индекс встретился в симуляции (в направлении DL).

**Что показывает:** какие модуляции реально используются. Если большинство столбцов слева (низкие MCS, QPSK) - канал в среднем плохой, абоненты далеко. Если справа (высокие MCS, 256-QAM) - канал хороший, абоненты близко. Это полезная диагностика качества сценария: если все столбцы сгруппированы у MCS 0–5, имеет смысл пересмотреть модель SNR или штрафа за удалённость.

## Вкладка «Полная таблица»

Интерактивная таблица всего DataFrame с колонками:

| Колонка | Что значит |
|---|---|
| TTI | Номер интервала времени (0 до `num_ttis-1`) |
| Direction | DL или UL |
| UE_ID | Идентификатор абонента |
| SNR_dB | Качество сигнала в этом TTI, дБ |
| MCS | Выбранный индекс модуляции и кодирования (0–27) |
| Resources | Строка вида «Nprb x 12 x Nlayers» - формат выделения |
| PRBs | Число выделенных PRB (парсится из Resources) |
| Payload_Bits | Размер пакета в битах |
| Codec | «LDPC Base Graph 1» или «LDPC Base Graph 2» |
| AXI_Load_Bytes | Нагрузка на шину AXI от PDSCH этого абонента |
| PDCCH_AXI_Bytes | Нагрузка на шину AXI от PDCCH (только DL) |
| Total_AXI_Bytes | Сумма AXI_Load_Bytes + PDCCH_AXI_Bytes |

Таблица поддерживает сортировку по любой колонке (клик по заголовку) и поиск. Высота фиксированная 500px, при превышении появляется скролл.
