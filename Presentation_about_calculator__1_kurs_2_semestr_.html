I. Актуальность и постановка задачи

Проблема

Аппаратное проектирование gNB

Кодеки LDPC и шина AXI требуют точной оценки нагрузки ещё до изготовления. Ошибка → переполнение буферов → обрыв связи за один TTI.

Критичность AXI-шины

Если шина не успевает передать I/Q-данные за TTI = 0,5 мс — буферы переполняются и связь прерывается.

Недоступность существующих решений

Коммерческие аппаратные эмуляторы недоступны для учебных и исследовательских студенческих проектов. Существующие открытые решения сложны в развертывании и не дают быстрой оценки нагрузки на внутренние шины.

II. Физический уровень 5G NR — Resource Grid

Resource Element (RE)

1 поднесущая × 1 OFDM-символ. Несёт 1 модулированный I/Q-символ

Resource Block (PRB)

12 поднесущих по частоте. При 100 МГц / SCS 30 кГц — 273 PRB

Нумерология SCS = 30 кГц

TTI = 0,5 мс, 14 OFDM-символов на слот. Чем выше SCS → тем быстрее кодек должен обрабатывать данные

PDSCH: символы 2–13

Используем 12 символов из 14 под данные (полный слот FDD) для стабильной работы генератора сетки без возникновения исключений.

bits_per_PRB = 144 × Qm × R  |  RE_actual = 144 (12 поднесущих × 12 символов)

Влияние MCS (3GPP TS 38.214)

MCS 0 — QPSK, Qm=2, R=0,117

Из 1 RE → 2 бита. 88% — служебные биты LDPC. Много PRB → большая нагрузка AXI

MCS 27 — 256-QAM, Qm=8, R=0,926

Из 1 RE → 8 бит. Тот же пакет занимает в ~24× меньше RE → в 24× меньше нагрузка AXI

Выбор LDPC Base Graph (3GPP TS 38.212)

BG2 — малые пакеты / низкая скорость кода

A ≤ 292 бит
A ≤ 3824 и R ≤ 0,67
R ≤ 0,25

BG1 — большие пакеты / высокая скорость кода

Во всех остальных случаях. Более сложный кодек — больше итераций декодера

MCS одновременно определяет число PRB, нагруженность кодека и объём трафика на шине AXI

III. Анализ существующих инструментов (Sqimway)

Что изучалось

Что даёт Sqimway

  • Визуализация Resource Grid в реальном времени
  • Настройка SCS, BW, режима дуплекса, числа антенн, CFI
  • Наглядное расположение физических каналов (PDSCH, PDCCH, RS…)
Чего не хватает → мотивация разработки

Нет расчёта нагрузки AXI

Sqimway показывает структуру сетки, но не считает, сколько I/Q-байт нужно передать по шине за TTI

Нет выбора кодека LDPC

BG1 vs BG2 определяет сложность декодера — ни один визуализатор этого не показывает

Нет симуляции абонентов

Только статичная картинка. Нет планировщика, нет динамики SNR, нет multi-UE сценария

Нет программного API

Только веб-интерфейс — нельзя встроить в расчёт, скрипт или автоматизацию

Наш калькулятор расширяет Sqimway: добавляет расчёт RE через py3gpp, LDPC, AXI и симуляцию MAC

IV. Алгоритм расчета ресурсов — 6 шагов

1

Таблица MCS

По индексу → Qm и R. Спект. эфф-ть = Qm × R

mcs_table = { 0: ('qpsk', 120, 2), 8: ('qam16', 553, 4), 16: ('qam64', 719, 6), 27: ('qam256', 948, 8) } R = R_target / 1024.0
2

Настройка py3gpp

nrCarrierConfig + nrPDSCHConfig

carrier = nrCarrierConfig() carrier.NSizeGrid = 273 carrier.SubcarrierSpacing = 30 pdsch = nrPDSCHConfig() pdsch.NStartBWP = 0 pdsch.NSizeBWP = carrier.NSizeGrid pdsch.SymbolAllocation = [2, 12]
3

Планировщик PRB

Количество PRB под пакет + смещение

bits_per_prb = 144 * Qm * R allocated_prb = ceil( (A + 24) / bits_per_prb) # Смещение антинаволжения end = min(start_prb + alloc, carrier.NSizeGrid) pdsch.PRBSet = range(start_prb, end)
4

Точный подсчёт RE

py3gpp учитывает DMRS (~108/PRB)

ind = nrPDSCHIndices(carrier, pdsch) # возвращает tuple или array if isinstance(ind, tuple): ind = ind[0] num_re = len(ind) # Ровно 144 RE на один PRB # При полном слоте FDD
5

Выбор LDPC

BG1 или BG2 по 3GPP TS 38.212

A = packet_bytes * 8 if A <= 292: codec = "BG2" elif A <= 3824 and R <= 0.67: codec = "BG2" elif R <= 0.25: codec = "BG2" else: codec = "BG1"
6

Нагрузка AXI

16 бит I + 16 бит Q = 4 байта/RE

axi_bus_bytes = num_re * 4 # Пример: 8 PRB, MCS 27 # num_re = 8 × 108 = 864 # AXI = 864 × 4 = 3 456 B/TTI

IV. Трудности при разработке и решения

🐛 Баг py3gpp: NStartBWP

nrPDSCHIndices() бросал исключение при выделении PRB не с нуля. Библиотека ожидала явного указания BWP.

# Исправление: pdsch.NStartBWP = 0 pdsch.NSizeBWP = carrier.NSizeGrid # Без этого — exception при start_prb > 0

🐛 nrPDSCHIndices возвращает tuple

В зависимости от конфигурации функция возвращала либо массив, либо кортеж. len() на tuple давал неверный результат.

ind = nrPDSCHIndices(carrier, pdsch) # Защита от обоих случаев: if isinstance(ind, tuple): ind = ind[0] num_re = len(ind) # теперь корректно

⚙️ Наложение PRB между абонентами

При выделении ресурсов нескольким UE их PRB накладывались — py3gpp давал неверные RE. Решение: параметр start_prb с нарастающим смещением.

current_prb = 0 for ue_id in active_users: res = calc(..., start_prb=current_prb) current_prb += alloc # сдвиг

⚙️ Баг библиотеки при нестандартной длине слота

При попытке выделить 9 символов для эмуляции защитного интервала, функция nrPDSCHIndices выдает IndexError. Решение: использование 12 символов под данные (полный слот FDD), что дает ровно 144 RE на один PRB.

# Решение: фиксированный SymbolAllocation pdsch.SymbolAllocation = [2, 12] # RE_actual = 144 (12 * 12)

IV. Реализация дуплекса FDD (Разделение DL и UL)

Два независимых массива
# Создаем независимые объекты TTI current_tti_dl = TtiSlot( tti_index=tti, users=[] ) current_tti_ul = TtiSlot( tti_index=tti, users=[] ) # Расчет идет параллельно process_link_direction('DL', current_tti_dl) process_link_direction('UL', current_tti_ul)

Специфика FDD

Прием (UL) и передача (DL) идут на разных частотах. В коде это реализовано как два независимых массива данных для каждого TTI.

Асимметрия трафика

Для Downlink генерируются тяжелые пакеты (до 1000 байт), для Uplink — легкие (до 300 байт) для эмуляции запросов и ACK.

Независимые ресурсы

Каждая линия (DL и UL) имеет свой независимый пул из 273 PRB. Наложения между направлениями физически невозможны.

IV. Справедливое планирование (Fair Scheduling)

Алгоритм ограничения ресурсов
# Жесткий лимит на одного абонента max_prb_per_ue = 40 current_prb = 0 for ue in active_users: # Запрашиваемые PRB по формуле 3GPP req_prbs = calc_prbs(ue.payload, ue.mcs) # Fair Scheduler: обрезаем жадных alloc_prbs = min(req_prbs, max_prb_per_ue) # Выделяем без наложения ue.start_prb = current_prb current_prb += alloc_prbs

Проблема «жадных» абонентов

Абонент с плохим сигналом (MCS 0) и большим пакетом может единолично занять все 273 PRB соты, заблокировав остальных.

Решение: Fair Scheduler

Введен жесткий лимит max_prb_per_ue = 40. Планировщик отрезает лишние запросы, сохраняя ресурсы.

Результат для оборудования

Гарантирует, что в один TTI ресурсы получат несколько абонентов, предотвращая монополизацию эфира и балансируя нагрузку на аппаратные блоки (AXI/LDPC).

Пик vs среднее — ×6.8

Пиковая нагрузка AXI (468 288 байт) превышает среднюю (68 731 байт) в 6.8 раза. Оборудование обязано проектироваться под пиковые пропускные способности.

Баланс кодеков (60% / 40%)

За счет моделирования 25 пользователей мы получили реалистичное распределение: BG1 (820 484) закрывает тяжелый DL-трафик, а BG2 (541 866) эффективно обрабатывает малые пакеты и большинство UL-сегментов.

Требования к пропускной способности

При пиковой нагрузке 468 288 байт за TTI (0.5 мс) минимальная аппаратная пропускная способность шины AXI должна составлять не менее 7.5 Гбит/с.
